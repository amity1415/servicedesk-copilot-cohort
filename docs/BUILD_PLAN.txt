IT Service Desk Copilot: 40-Session Build Plan
Nov 15, 2026 · @Amit
One use case carries all 60 hours: an assistant that answers employee IT questions and resolves requests through the ticketing system and asset database. Each of the 40 sessions adds one capability to the same repository, and the release tagged after session 40 is the final project.
Problem statement
Build a production-grade assistant that resolves employee IT requests end to end, on synthetic data, with every step measurable.
Background. A fictional company with about 10,000 employees runs an IT service desk. It handles password and multi-factor authentication (MFA) problems, VPN and software issues, access requests, device faults and new-joiner setup. The answers exist, but they are scattered across knowledge-base (KB) articles, policy PDFs, runbooks and old tickets, often in several versions.
Analysts spend much of their time searching, asking for missing details and routing tickets. Access requests wait in approval queues, and similar tickets get different answers.
The assistant must:
1.  Answer IT questions from the company's own documents, cite its sources, and say when the answer is not there.
2.  Diagnose a request using live data: the employee's devices, licences, open tickets and known outages.
3.  Resolve it by acting on enterprise systems: raising, updating and routing tickets, and fulfilling access and software requests.
4.  Stay inside each user's permissions, get human approval before risky actions, and ignore instructions hidden in tickets or documents.
5.  Prove its quality: scored against historical tickets, traced end to end, monitored for cost and latency, and deployed as containers.
Systems, all simulated. Documents (KB articles, IT policies, runbooks, software catalogue), a database (employees, devices, licences, service status) and a ticketing API (tickets, comments, assignment groups, resolutions).
Users. Employees ask and request. Analysts and managers approve risky actions. Engineers run and monitor the system.
Out of scope. Real company data, a live ticketing product and a real identity provider. Each is replaced by a simulated service that can be swapped later.
The finished system
A request enters through the app, the supervisor routes it to a specialist, and every action on an enterprise system goes through an MCP server that checks the caller's role. Any agent may use any server its role allows; only the HR agent, which another team owns, is reached over A2A.
Roadmap
Each 90-minute session follows one rhythm: about 20 minutes of concept, 55 of building, and 15 to run the check and commit. A module is finished only when its gate passes.

Module 1: ML and transformer foundations (sessions 1 to 4)
Module 1 sets up the repository and teaches ML basics on the historical tickets, ending with the first model call.
Session

1. Kickoff and project setup
Enterprise use case kickoff; VS Code project setup (Python, Git, environment and secrets management)
Create the repository with a src layout, settings loaded from .env, structured logging, pre-commit hooks for lint and secret scanning, and a first test. Load the historical tickets and print counts by category.
A clean clone installs and passes pytest and pre-commit; no secret is in Git.
2. ML basics on ticket data
ML basics: supervised and unsupervised learning, training, evaluation metrics
Train a category and priority classifier (TF-IDF plus logistic regression) on a train and test split. Cluster tickets with k-means to surface recurring issues. Write precision, recall, F1 and a confusion matrix to reports/.
The report is committed and names the weakest class and why it is weak.
3. Neural networks, transformers and tokenization
Neural network basics; transformer architecture, attention, tokenization
Swap in a small neural network (MLPClassifier) and compare it with logistic regression. Write a token report: tokens per article and ticket, how the tokenizer splits error codes and KB IDs, and estimated cost per ticket.
The model comparison and the token report are in reports/.
4. Inference parameters and the first LLM call
LLM inference parameters; calling an LLM API from Python
Write llm/client.py, one wrapper with timeout, retry, and token and latency logging. Classify and summarise tickets zero-shot at temperature 0, then compare accuracy, cost and latency with the session 2 classifier. Add a CI workflow that runs lint and tests with the model mocked.
The comparison is in a decision record; CI is green without calling a paid API; tag v0.1-foundations.

Module 2 builds the knowledge assistant: a thin pipeline in session 5, then one stage improved per session and measured on golden questions from the start.

5. Why RAG, and a naive baseline
Problems RAG solves (hallucination, stale and private knowledge); RAG architecture
Ask the bare model a company VPN policy question and record the invented answer. Then build the thinnest pipeline: 20 Markdown articles, fixed chunks, in-memory vector search, one prompt. Write the first 20 golden questions from resolved tickets.
ask "How do I set up VPN on a Mac?" answers from the KB; 20 golden questions are in evals/.
6. Document ingestion and parsing
Document ingestion and parsing
Write loaders for PDF, DOCX, HTML and Markdown that produce one Document model with metadata: type, system, OS, region, audience, version, effective date. Keep tables readable. Make ingestion repeatable with content hashes and log every skipped file.
The whole corpus ingests; a second run adds nothing; the SLA table survives as readable text.
7. Chunking I: fixed and recursive
Chunking strategies (fixed, recursive)
Define one chunker interface with fixed-size and recursive, heading-aware strategies. Add a script to inspect chunks, and tests on size, overlap and boundaries.
Recursive chunks never split a numbered troubleshooting step; the strategy is chosen in config.
8. Chunking II: semantic and parent-child
Chunking strategies (semantic, parent-child)
Add semantic chunking by embedding similarity. Add parent-child chunking for long policies: small chunks are searched, the parent section is returned as context.
All four strategies run on the corpus; Recall@5 per strategy is recorded on the 20 golden questions.
9. Embeddings
Embeddings
Build an embedding module with batching, retry and a cache keyed by content hash. Compare two embedding models on the golden questions. Show how poorly error codes and KB IDs match by meaning alone.
Every chunk is embedded and cached; the model choice and its numbers are in a decision record.
10. Vector database and indexing
Vector databases and indexing
Run PostgreSQL with pgvector in Docker Compose. Store chunks, vectors and metadata, and build an HNSW index. Handle updates and withdrawals so stale chunks are removed.
Top-k search runs from the database; re-ingesting a changed article replaces its chunks; query latency is recorded.
11. Retrieval and metadata filtering
Metadata filtering; retrieval
Build a retriever with top-k, a score threshold and filters for OS, region, audience and current version. Apply the audience filter before the search so restricted runbooks never reach an employee.
Tests pass: a macOS user gets no Windows steps, superseded policies never appear, employees see no IT-only runbooks.
12. Hybrid search
Hybrid search (keyword plus vector)
Add keyword search with PostgreSQL full-text search and merge it with vector results by reciprocal rank fusion. Add golden questions that contain error codes and KB IDs.
"VPN error 809" finds its article; the scorecard compares vector, keyword and hybrid.
13. Reranking and query rewriting
Reranking; query rewriting
Retrieve 30 candidates and rerank to 5 with a cross-encoder. Rewrite follow-ups such as "it still doesn't work" into standalone queries from the conversation, and expand internal acronyms.
Two-turn tests retrieve the right article; the scorecard shows the gain and the added latency.
14. Grounded prompting with citations
Grounded prompting with citations
Write a versioned answer prompt that uses only retrieved context, cites article and section, prefers the newest effective date, and abstains when the KB has no answer, offering to raise a ticket. Check that every citation points to a retrieved chunk.
Requests 1 and 2 are answered with valid citations; out-of-scope questions get an abstention; both are covered by tests.
15. RAG evaluation
RAG evaluation (Recall@k, context precision, faithfulness, answer relevance)
Grow the golden set to about 100 questions, including unanswerable ones. One command reports all four metrics. Tag ten failures by cause: retrieval miss, bad chunk or generation.
The report compares the session 5 baseline with the current pipeline on all four metrics.
16. RAG as a FastAPI service
RAG exposed as a FastAPI service
Expose POST /ask, /health and /ingest with typed request and response models, streaming, API-key auth, request IDs in logs and clean error responses. Add a Streamlit chat page that shows citations.
API tests pass in CI; requests 1 and 2 work in the UI; tag v0.2-rag.

Module 3 turns the assistant into an agent that acts: tools first, then a hand-written loop, then LangGraph, with approval, multiple agents and guardrails added on top. Sessions follow build order, so LangGraph arrives in session 20, earlier than in the syllabus list.

17. Agents vs workflows
Agents vs workflows
Add the mock ticketing API and the seeded employee and asset tables to Docker Compose. Code the password-reset request as a fixed workflow. Sort every planned action into read, low-risk write or approval-required in policies/actions.yaml.
The workflow raises a ticket through the API; every action has a risk tier.
18. Tool calling and structured output
Tool and function calling; structured output
Write tools with typed inputs and unit tests: search_kb, get_employee, get_assets, check_service_status, create_ticket, update_ticket. Define a TicketDraft schema (category, priority, summary, steps tried, asset, assignment group) with one repair attempt on invalid output.
The model picks the right tool for 10 sample requests; 20 requests produce schema-valid tickets.
19. The agent loop (ReAct), written by hand
Agent loop (ReAct)
Write a reason, act, observe loop in about 100 lines over the session 18 tools, with a step limit and a readable step log. Run it on "My laptop is slow".
The loop checks the device and outages, searches the KB and proposes steps; a runaway loop stops at the limit.
20. LangGraph and state management
LangGraph; state management
Port the loop to a LangGraph graph with typed state, a tool node, conditional routing and streaming. Add a PostgreSQL checkpointer so each conversation is a thread that can resume.
Request 3 passes in LangGraph; a conversation resumes after the process restarts.
21. Planning and task decomposition
Planning and task decomposition
Add a planner node that turns "Set up a new joiner starting Monday" into ordered steps with dependencies: account, laptop, licences, access groups. An executor works through the plan and replans when a step fails.
The plan is stored in state and shown in the UI; steps that need no approval complete.
22. Short-term and long-term memory
Short-term and long-term memory
Trim and summarise long conversations to a token budget. Store long-term memory per employee (devices, past issues, preferences), with a rule for what may be saved and a delete-on-request function.
A new thread recalls last month's VPN issue; long chats stay in budget; the deletion test passes.
23. Agentic RAG and reflection
Agentic RAG; reflection
Make retrieval a decision: the agent chooses whether to search, grades what it gets, rewrites and retries, and combines a policy with a how-to article. Add a self-check that the draft answer is supported by its sources.
A two-document question is answered with citations to both; an unsupported draft is caught and revised.
24. Self-correction, error handling and retries
Self-correction; error handling and retries
Return tool errors as structured results the model can correct. Add timeouts, retries with backoff, idempotency keys on ticket creation, step and cost budgets, and escalation to a human when stuck. Turn on fault injection in the ticketing mock.
With faults on, no duplicate ticket is created and every request ends in success or a clean escalation.
25. Human-in-the-loop approval
Human-in-the-loop approval
Pause the graph before approval-required actions and show the request on an approvals page with approve, edit and reject. Keep the rules for who approves what in policies/approvals.yaml. Write every decision to an audit table.
Request 4 runs to fulfilment after approval; a test proves no gated tool runs without an approval record.
26. Multi-agent I: supervisor and specialists
Multi-agent patterns (supervisor)
Split the agent into knowledge, diagnostics (read-only tools) and fulfilment (write tools) agents under a supervisor, each with its own prompt and tool allow-list. Compare with the single agent on 15 tasks for quality, tokens and latency.
Requests 3 and 4 pass through the supervisor; the comparison is in a decision record.
27. Multi-agent II: hierarchical teams and handoffs
Multi-agent patterns (hierarchical, handoffs)
Add an onboarding team with its own lead under the supervisor. Add handoffs between agents and to a human analyst that pass a case summary: steps tried, evidence, suggested next step.
The IT steps of request 5 run through the onboarding team; an unresolved case reaches the analyst queue with a full summary.
28. Guardrails and prompt injection defence
Guardrails and prompt injection defence
Treat ticket text, documents and tool results as data, never as instructions. Add input and output checks, PII masking in logs and per-role tool limits. Write about 25 attacks into evals/redteam/ and fix what gets through.
Request 6 and the rest of the red-team set fail safely from one command; tag v0.3-agent.
Module 4: MCP and agent interoperability (sessions 29 to 34)
Module 4 moves the tools out of the agent's process into three MCP servers, adds real permissions, and connects the HR team's agent over A2A.

29. MCP architecture and the ticketing server
MCP architecture (host, client, server); custom MCP server (ticketing)
Build a ticketing MCP server over stdio with create, update, search and comment tools that wrap the ticketing API. Inspect it with MCP Inspector, then connect the agents through an MCP client in place of the in-process tools.
The agent raises a ticket through MCP; the session 28 tests still pass.
30. Tools, resources and prompts: the documents server
Tools, resources and prompts; custom MCP server (documents)
Build a documents MCP server with a search tool, KB articles as resources addressed by URI, and two reusable prompts: triage a ticket and summarise an incident.
A client exercises all three primitives; the knowledge agent answers through the server.
31. The database server and transports
Custom MCP server (database); transports
Build a database MCP server with fixed, parameterised query tools (employee, assets, licences, service status) on a read-only role with row limits. Move all three servers to streamable HTTP and run them as Compose services.
The agents work unchanged against three HTTP servers; a test proves the database role cannot write.
32. Authentication and permissions
Authentication and permissions
Verify a bearer token in each server and act as the signed-in user. Map roles (employee, analyst, admin) to tools in policies/tool_permissions.yaml, limit employees to their own tickets and devices, and log every tool call.
Permission tests pass for three roles; a denied call is logged and returns an error the agent can explain.
33. Agent-to-Agent (A2A) with the HR agent
Agent-to-Agent (A2A) protocol
Run a small HR onboarding agent as a separate service, treated as another team's product, with an agent card at /.well-known/agent-card.json. The onboarding team delegates the HR steps to it and waits for the long-running task.
Request 5 completes with the HR steps done over A2A; an unauthenticated call is rejected.
34. MCP vs A2A vs direct function calling
MCP vs A2A vs direct function calling
Build "check service status" three ways and measure latency and code needed. Record when to use each, by ownership, number of consumers and trust boundary. Add contract tests that snapshot every MCP tool schema.
The decision record is merged with its measurements; a breaking schema change fails a test; tag v0.4-mcp.

35. Evaluation strategy and golden datasets
Evaluation strategy; golden datasets
Write the evaluation plan: what is measured at retrieval, answer, tool-call and task level. Build about 40 agent tasks from historical tickets, each with user, expected tool calls, expected end state and forbidden actions. Add a one-command environment reset.
The task set passes a schema check and a review; the reset restores the database and tickets.
36. LLM-as-a-judge
LLM-as-a-judge
Write judges for answer quality and ticket summaries, with rubrics in evals/rubrics/. Label 30 examples by hand, measure agreement between judge and human, and revise the rubric. Use a code check wherever a rule can be tested exactly.
Judge and human agreement is reported and meets the release target.
37. Agent evaluation
Agent evaluation (task success, tool-call accuracy, trajectory)
Build a runner that checks the end state in the database and ticketing system, scores tool choice and arguments, and checks order rules: policy check before access request, approval before fulfilment, no forbidden calls.
One command reports task success, tool-call accuracy and trajectory results; the baseline is recorded.
38. Regression testing in CI
Regression testing in CI
Make the CI workflow start the Compose stack and run lint, unit and contract tests, a smoke evaluation and the red-team set, with thresholds as gates. Run the full evaluation nightly. Pin model, prompts and index version in release/manifest.yaml.
A deliberately worse prompt is blocked by CI.
39. Tracing, observability and monitoring
Tracing and observability; monitoring cost, latency and quality
Add OpenTelemetry traces across the API, agents, MCP servers and model calls, with tokens, cost and role on each span and PII masked. Build a dashboard for cost per resolved request, p95 latency, tool error rate and sampled answer quality. Add a feedback button to the UI.
One request can be followed across every service in the trace view; the dashboard shows live numbers.
40. Containerization, production readiness and final walkthrough
Containerization and production readiness; final walkthrough of the completed use case
Harden the images: pinned dependencies, non-root user, health checks, image scan. Finish the readiness checklist: secrets, rate limits, timeouts, graceful shutdown. Run the demo script of the six requests with traces and the evaluation report.
docker compose up on a clean machine passes the demo script; the release targets hold; tag v1.0.
